# <项目名> Constitution（ToB 后台管理系统通用版）

> 由两个内部 ToB 项目 Owner 逐项拍板的治理原则沉淀而成。
> 接入新项目：替换 `<项目名>`；各原则末尾的「理由」按本项目业务改写；
> 修订 MUST 经项目 Owner 确认，版本号语义见 Governance。

## Core Principles

### I. Spec 只写 WHAT（规范即真相源）

spec.md 是唯一业务需求真相源，MUST NOT 含实现细节（表结构、DDL、接口路径、
框架选型、视觉设计均归 plan/UI 阶段）。Spec Kit Preview 为固定步骤：
低保真原型是 spec 的**零虚构投影**——spec 未定义的控件/字段/状态禁止出现在原型上。
任何 spec 修改后 MUST 通过双核查：① spec-kit 规范合规（FR 均 MUST、NC 清零、
无实现措辞泄漏）；② 前后一致性冲突扫描——低级冲突自行修复，中高级冲突 MUST
列证据交人工拍板。`NEEDS CLARIFICATION` 提交前清零。
FR 区 MUST 以粗体分组标题行按实体的增删改查行为分组（一个标题＝一个实体/流程段的
完整 CRUD 集合，组内按 增→删→改→查 排列；流程/状态机型条款按业务流程段分组），
MUST NOT 以页面/控件作 FR 主语。

理由：本项目以 spec 驱动 AI 辅助开发，真相源被污染 = 全链路失真；原型混入
无依据内容会误导人工评审。

### II. 界面三条铁律（简单易理解·人工介入少·单屏不过载）

北极星：**使用者每天只做三件事——丢物料、清黄格、点亮着的按钮**；
其余一律系统自动或置灰不可见。硬约束：表格主列 ≤6、异常置顶一致项折叠、
不可达操作不在工作台出现、用户可见文案零黑话。
新增功能优先级排序：减少需理解的信息 > 减少操作步骤 > 减少等待不确定性 >
降低错误成本 > 保持流程连续性。ToB 高强度操作（批量/长等待/大数据量/高风险/
连续录入/复杂配置/长流程）MUST 给人为关怀：明确进度、告知预计耗时、解释正在发生
什么、下一步建议、完成后适度正向反馈。

理由：使用者是每天重复操作的业务员工，低认知负荷是第一产品原则（P1）。

### III. AI 只提候选，人下结论（零事故底线）

AI 在任何审查/比对/改稿/识别场景中 MUST NOT 直接生效判定：✅结论只能来自
确定性比对或人工确认（任何置信度不例外，系统 MUST NOT 提供阈值/严格模式等
放宽开关）；AI 产出 MUST 差异对比或候选列表呈现、人工「采纳」后才生效；
AI 候选 MUST 通过原文逐字回查，回查不到即丢弃记日志；AI 不可用 MUST 降级透明
（界面明示、分母不缩、需 AI 项转待人工）。对外物料 MUST NOT 含内部事项
（待确认/AI 术语/覆盖率）。严重级异常绝对不可人工放行。

理由：判定错一位即资产/资金损失级别事故；零事故且可完整回放是底线要求。
（无 AI 参与判定的项目此条仍保留——它是新增 AI 功能时的准入门槛。）

### IV. ToB 不做绩效游戏化（人文关怀红线）

MUST NOT 存在积分、连击、徽章、成就墙、排行榜等任何把劳动量数值化/比较化的元素
——ToB 工作工具中此类设计＝绩效 PUA。允许的反馈仅限平实、具体的结果确认
（禁幼儿化褒奖）。人文关怀（高强度提醒休息/深夜安抚/节前收尾/连续异常宽慰）MUST：
一次性、可静音、永不拦截操作；关怀记录本人私有，MUST NOT 提供任何个人工时/
操作量/加班频次的管理侧报表。失败/驳回/拦截场景零庆祝。

理由：ToB 工具的服务对象是每天处理业务的操作员，关怀不得变质为监控。

### V. 台账是数据唯一权威（一致性即正确性）

业务台账是全部下游取数的权威源；派生物料 MUST NOT 旁路台账属性另存一份。
硬约束：金额全链路以最小货币单位整数运算；关键编码（如商品编号、单据号）
全局唯一一物一号；业务节点完成瞬间对引用值冻结快照，档案此后改动 MUST NOT
污染历史单据；mock/示例数据 MUST NOT 作为正式取数来源；业务状态字段 ≠
数据层软删除，两机制独立实现。审计日志只增不删改、支持完整回放。

理由：纠纷处理与合规追索全靠台账可追溯；可追溯是底线。

## 质量门禁 *(mandatory)*

- **G1 新手标准**：新手只看用户手册 30 分钟内独立走完培训例（走完总纲 P1 主流程
  闭环；培训例定义随总纲 spec 落定）。做不到＝界面返工。
- **G2 状态安全**：非法状态跳转拦截率 100%；审计时间线可完整重放任一业务对象历史。
- **G3 AI/自动判定零事故**：凡涉及判定/识别的功能，黄金集盲测关键字段召回率 100%、
  差错判率=0；每条 ✅ 可追溯到确定性比对或人工确认；无一条仅凭 AI 自动通过。
- **G4 违反本宪法的方案 MUST NOT 进入实现阶段**；确需例外，MUST 在对应 spec 的
  Assumptions 显式记录例外内容与原因并经 Owner 批准。
- 门禁核验方式：各模块 spec 的 Acceptance Scenarios / Independent Test 即验收脚本，
  plan 阶段 MUST 将其映射为自动化测试任务。

## 交付与流程治理

- **交付顺序**：以总纲 spec 的 P1/P2/P3 定序为准，后续批次随 spec 演进登记。
- **模块拆分纪律**：平级 `specs/NNN-slug/`；FR/US/SC 编号全局唯一，拆分/迁移不重编号，
  跨模块引用直接用编号；跨模块条款改动 MUST 双向同步。
- **版本控制**：每次 commit 后 MUST push 同步远程，并以 `git rev-parse HEAD` 与
  `git rev-parse origin/<branch>` 比对一致才算成功；commit message 禁用
  `feat:`/`fix:`/`chore:` 等 conventional 前缀。
- **原型同步**：任一模块 spec 变更 → 自动重生成受影响原型页并更新 PREVIEW.md
  映射与决策日志；原型层决策（布局/交互琐事）只记日志，不回写 spec。
- **UI 真相源**：所有 UI 实现 MUST 遵循仓库根 `DESIGN.md`；无 `DESIGN.md`
  不得写任何前端代码（先补并经 Owner 确认）。

## Governance

- 本宪法由项目 Owner（用户）批准与修订；AI 代理仅提案，修订 MUST 经 Owner 确认。
- 修订流程：提出 diff → Owner 拍板 → 更新版本号与本文件 → 同步检查各 spec 是否有
  条款因原则变化需要联动（尤其 Assumptions 拍板记录组）。
- 版本号语义：MAJOR＝删除或重定义原则；MINOR＝新增原则或门禁；PATCH＝措辞澄清。
- 解释优先级：spec 条款编号（判例）> 本宪法原则 > 通用惯例。冲突时以 Owner 裁决为准。
