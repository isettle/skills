# spec-kit 物料落位与回写规则（ToB 后台）

> 回答两个高频争议：①「这条内容写进哪个物料文件」②「原型改了要不要回写 spec」。
> 例子域：电子商城后台——运营新建商品，点「创建」按钮弹出填写弹层。

## 一、落位表：每类内容住哪儿

| 内容类型 | 物料文件 | 电子商城示例 |
|---|---|---|
| 需求原始入口（说明/痛点/草稿/泳道图＋拷问记录） | `specs/NNN-*/intent.md`（流程最前端，先于 constitution/specify；GI 门禁＝四段齐备＋grill-with-docs 拷问完成；spec 定稿后冻结为溯源快照） | 「运营每天靠聊天记录核退款，20 分钟/单」＋退款泳道图＋拷问轮次与术语表 |
| 业务规则（WHAT/WHY） | `spec.md`（FR MUST / US / SC / Key Entities / Edge Cases / Assumptions） | `FR-010: 创建商品前系统 MUST 要求操作人确认价格与库存`；`US1: 运营 3 分钟内完成上架` |
| 页面级交互规则（按钮名称、弹层还是抽屉、字段布局、多步表单） | `DESIGN.md` 交互行为章 + `preview/*.html` 原型（放 feature 目录内，与 spec 一起版本化） | 「创建」按钮 → 点开出价弹层；弹层放 ≤8 个字段；提交按钮 pending 文案「保存中…」 |
| 操作走查步骤 | `quickstart.md`（plan Phase 1 产物） | 「打开商品列表 → 点创建 → 弹层出现 → 填价格 → 点确认」 |
| 数据字典（实体/字段/关系/状态机流转表） | `data-model.md` | 商品实体字段表、上下架状态机逐转移表 |
| API 文档 | `contracts/api.md`（机器可读优先） | 创建商品接口的请求/响应字段表 |
| 技术选型/架构 | `plan.md` / `research.md` | 选 Go+React 还是 FastAPI、部署方式 |
| 治理红线 | `constitution.md` | AI 判定不得直接生效 |

**spec 里禁止出现**：表名、字段类型、DDL、HTTP 路径、框架/库名、视觉设计，以及「点击XX按钮」「弹出弹层」「跳转到XX页」等控件级措辞。
**状态枚举分层**：状态有哪些、合法/非法流转 = spec（WHAT 层，写成 FR MUST）；逐转移表（当前态×动作×触发方→目标态+副作用）= `data-model.md`，并在 spec Assumptions 里注明交接。

## 二、一句话判据（两道测试）

1. **换技术栈测试**（定 spec vs plan/data-model/contracts）：把 Web 后台换成原生 App，这句话还成立 → spec；失效 → 挪走。
2. **换 UI 测试**（定 spec vs DESIGN/原型）：把弹层换成抽屉/新页面，这条规则的语义还在 → 语义写 spec（如「操作人 MUST 二次确认」），形态写 DESIGN.md；整句随 UI 变形（如「点击创建弹出 Modal」）→ 只进 DESIGN.md + 原型。

## 三、原型改动回写决策树（三分类）

| 序号 | 变化类型 | 判定 | 动作 | 例子 |
|---|---|---|---|---|
| ① | 业务规则冲突 | 原型与 spec.md 打架 | 以 spec.md 为准改原型；若原需求本身变了，**先改 spec.md 再同步原型** | spec 要求上架前确认，原型做成直接提交 → 改原型 |
| ② | 纯 UI 表达 | 换端后规则不变、用户完成任务的步骤/义务/风险不变 | 只改原型 + 记 PREVIEW.md 决策日志，不回写 spec.md | 弹层→抽屉、按钮从右上挪到左上 |
| ③ | 实质交互变化 | 触及任一：**完成步骤数、确认义务、数据丢失风险、系统行为** | 不得直接归 ②；先判定是否构成需求变化：是 → 走 ① 先改 spec（写成 FR）再同步原型与 quickstart；否 → 才降级 ② | 见下 |

②与③分界例（电子商城）：

- 确认弹层改成抽屉 → ②（义务还在）
- 去掉确认弹层、点创建直接落单 → ③（确认义务消失 = 需求变化 → 先改 spec）
- 弹层右上角 × 关闭时不提示丢弃已填内容 → ③（引入数据丢失风险）
- 弹层字段从 5 个减到 3 个、必填变选填 → ③（影响任务完成要素）

③ 的作用：在过两道判据之前先做一次「这是不是换了端也带不走的东西」的审查，防止把行为变化藏进「UI 微调」的标签里。

## 四、维护红线（防来回打架）

1. spec.md 是唯一权威源：原型与 spec 不一致时永远改原型，不得反向改 spec 迁就演示。
2. 页面↔FR 映射只维护在 `preview/PREVIEW.md`；方向永远 spec→原型，不得由页面反推 FR。
3. 不许借原型往 spec 塞不规范内容；也不许借「UI 调整」名义悄悄改需求——③ 类变化必须显式走 spec 修订。
4. spec 每次变更后自动重生受影响原型页并更新 PREVIEW.md 映射表与决策日志（不等用户叫）。
